# Data and authority boundaries

## Present validation tooling

The maintained checkout and selected development environment are trusted execution inputs. The tools are repository checks, not a sandbox for an arbitrary checkout or a model-execution permission system. Source changes, native program selection and environment installation require their ordinary review and provenance controls.

| Input or asset | Current control | Remaining boundary |
| --- | --- | --- |
| Repository descriptor and inventory | Fixed expected identity/state/schema, strict bounded input admission and independent source binding | A digest proves byte identity; it does not prove scientific meaning or global registration |
| Public source and attribution | Explicit cohort, required path kinds, source/configuration selection, native headers, exact sidecars and original-byte checks | Known cache contents and private documentation are outside this named source cohort |
| Ignore and Git metadata | Selected ignore bytes plus actual root/branch/remote/index and finite ignore probes | Probes alone do not prove every possible ignore result; this is not a history or remote-transport assessment |
| Documentation configuration and native output | Selected configuration before native build, then actual source/HTML/link/anchor/API inspection | Direct inspection cannot attest the producer or browser behaviour |
| Development packages and native programs | Selected lock/provenance inputs, installed metadata and selected native file identity | Matching metadata does not verify every package payload byte or reproducible binary build |
| Source scanner and source software inventory | Temporary public projection; explicit native inventory root and declared ancillary exclusions | Scanner success is scoped to the inspected source, and inventory checksums are not authenticity |
| Report and generated output | Fixed caller-safe diagnostics, bounded reads, explicit destinations and exclusive inventory creation | No concurrent-source snapshot or power-failure durability is claimed |
| Child processes | Maintained no-shell argument vectors, direct-child deadlines, reaping and private temporary logs | Completed-output limits are not a live volume ceiling; each nested tool owns its descendants |

No received metadata can enable a more permissive validator, populate initial qualified capabilities, select a native executable or turn an unavailable tool into success. All required preflight results remain visible. A focused selection leaves other requirements unexecuted and refuses complete acceptance.

Native vulnerability checks query the declared public development-package graph. Native bootstrap downloads the selected public tool archives only when explicitly invoked. Metadata, inventory and documentation inspection do not execute a supplied model or upload model inputs. There is no publication, signing, device-control or deployment step in the current validation chain.

The full source checks apply to the selected repository cohort and actual declared limits. They do not certify whole-machine isolation, every cache entry, remote services or the integrity of an untrusted operating system. Unsupported source/configuration changes require reviewed policy updates; received data cannot approve its own policy.

## Planned model and evidence boundaries

The planned harness handles supplied model descriptions, inputs, external framework outputs and evidence references. These inputs do not grant execution, signing, deployment or publication authority. Model execution belongs only to explicitly selected supported drivers with declared limits.

Evidence content, a successful transport response and a valid signature have different meanings. Signature verification establishes only its admitted envelope facts; source identity, numerical semantics, current eligibility and comparison results need their own evidence. Inspection must display unavailable or unverified references explicitly.

The domain design requires bounded input admission, explicit output destinations and immutable attempt records. A partial or failed attempt must not be repaired into success by dropping outputs, changing a seed, selecting a different lane or overwriting the prior record. Ordinary failures need caller-safe diagnostics without private paths or environment contents.

The model-execution engine, drivers, comparison methods and operational custody are unimplemented. No model-runtime isolation, device control, numerical reliability or operational recovery qualification is claimed. The present tooling controls do not qualify those future boundaries.
